RPC — это парадигма удалённого вызова процедур, при которой одна программа может вызвать функцию или метод, выполняемый на другом сервере, как будто это локальный вызов. Это фундаментальный способ организации взаимодействия между распределёнными компонентами.

---

## 📌 Общая характеристика

- **RPC** скрывает сетевую природу вызова — вызывающая сторона не знает, что код выполняется на удалённой машине
    
- Основной фокус: **действия и операции**, а не ресурсы (в отличие от REST)
    
- Используется в разных реализациях: gRPC, JSON-RPC, XML-RPC, Thrift, Apache Avro
    

---

## 🧠 Принцип работы

1. Клиент вызывает локальную "обёртку" функции
    
2. Обёртка сериализует данные (аргументы вызова)
    
3. Запрос отправляется по сети на удалённый сервер
    
4. Сервер десериализует запрос и вызывает соответствующую функцию
    
5. Ответ возвращается по тем же шагам в обратном порядке
    

Сеть и сериализация/десериализация **прозрачны** для программиста

---

## ⚙️ Компоненты

- **Stub (обёртка)** — клиентская часть, которая делает удалённый вызов "прозрачным"
    
- **Skeleton** — серверная часть, принимающая запросы и вызывающая реализацию
    
- **Protocol** — определяет правила сериализации и сетевого обмена (JSON, Protobuf, XML)
    
- **Transport** — TCP, HTTP/2, WebSocket и др.
    

---

## 📘 Примеры реализаций

### JSON-RPC:

- Простой формат поверх HTTP
    
- Использует JSON для передачи методов и параметров
    
- Пример запроса:
    

```json
{
  "jsonrpc": "2.0",
  "method": "add",
  "params": [1, 2],
  "id": 1
}
```

### gRPC:

- От Google, использует Protocol Buffers (protobuf) для сериализации
    
- Передаёт данные поверх HTTP/2
    
- Высокая производительность и поддержка стриминга
    

### Thrift:

- От Apache, также использует бинарную сериализацию
    
- Поддерживает множество языков
    
- Позволяет гибко описывать сервисы и типы
    

---

## 📚 Сравнение RPC и REST

|Характеристика|RPC|REST|
|---|---|---|
|Ориентация|На действия (функции)|На ресурсы (объекты)|
|URL|`/getUser`|`/users/1`|
|Формат данных|JSON, Protobuf, XML|JSON, XML|
|Стандарты|Разные протоколы, нет единого|Чётко определён (HTTP)|
|Кэшируемость|Обычно отсутствует|Поддерживается|
|Простота дебага|Ниже (особенно бинарные форматы)|Выше|
|Производительность|Выше при использовании бинарных форм|Зависит от реализации|

---

## ✅ Преимущества RPC

- Естественная модель вызова методов
    
- Высокая скорость (особенно при бинарной сериализации)
    
- Поддержка стриминга (в gRPC)
    
- Явная типизация (например, через `.proto` в gRPC)
    

---

## 🚫 Недостатки RPC

- Сложнее отлаживать (особенно бинарные протоколы)
    
- Меньшая гибкость (жестко заданные методы)
    
- Проблемы совместимости при изменении API
    
- Часто не поддерживает кеширование и маршрутизацию на уровне HTTP-прокси
    

---

## 📌 Когда использовать RPC

- Низкоуровневые системы с высокими требованиями к производительности
    
- Микросервисные архитектуры внутри одного домена (например, между backend-сервисами)
    
- Сценарии со стримингом данных (аудио/видео/логирование)

### 📄 Пример `.proto`-файла для gRPC

```
syntax = "proto3";

package user;

service UserService {
  rpc GetUser(GetUserRequest) returns (GetUserResponse);
}

message GetUserRequest {
  int32 user_id = 1;
}

message GetUserResponse {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
```

Этот файл определяет:

- Сервис `UserService` с методом `GetUser`
    
- Сообщения-запросы и ответы (типизированные структуры)
    

gRPC автоматически генерирует код клиента и сервера на разных языках (например, Go, Python, Java, C#), обеспечивая строгую типизацию и высокую производительность за счёт использования Protocol Buffers.
