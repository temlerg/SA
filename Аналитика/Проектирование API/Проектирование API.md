
---

## 1. 🔑 Основные понятия

- **API (Application Programming Interface)** — интерфейс взаимодействия между системами/компонентами.
    
- **[[REST API]]** — архитектурный стиль, основанный на HTTP и CRUD-операциях.
    
- **[[SOAP]]** — протокол обмена сообщениями с жёсткой структурой.
    
- **[[GraphQL]]** — язык запросов к API, позволяющий клиенту самому определять структуру ответа.
    
- **[[RPC]] (Remote Procedure Call)** — модель вызова удалённых процедур, при которой API представляет собой набор функций с параметрами и результатом. Часто используется в gRPC, Thrift, JSON-RPC и других протоколах. RPC ориентирован на действия, а не на ресурсы.
---

## 2. 📐 REST: принципы и стандарты

### Основные методы:

- `GET` — получение данных
    
- `POST` — создание ресурса
    
- `PUT/PATCH` — обновление ресурса
    
- `DELETE` — удаление ресурса
    

### Принципы REST:

- **Именование ресурсов** через URL (`/users`, `/orders/123`)
    
- **Статусы HTTP**: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 500 Internal Server Error
    
- **[[REST Безопастность]] и [[Идемпотентность]]** методов (`GET` не должен менять данные)
    
- **Использование JSON** как основного формата

## 3. 📋 Контракты API

Системный аналитик часто пишет спецификации (контракты):

- Структура запросов и ответов
    
- Описание параметров, заголовков, кодов ошибок
    
- Формат JSON-сообщений
    

Пример ответа:

```json
{
  "id": 1,
  "name": "Ivan",
  "email": "ivan@example.com"
}
```

## 4. 📘 Документация API

Стандарты документации:

- **OpenAPI/Swagger** — YAML/JSON-документация API
    
- **Postman** — описание, тестирование и коллекции запросов
    
- **Redoc** — визуализация Swagger-документации
    

---

## 5. 🔐 Аутентификация и авторизация

- **Basic Auth**
    
- **Bearer Token / JWT**
    
- **OAuth 2.0** — делегированная авторизация (например, через Google, GitHub)
    

---

## 6. 🧪 Тестирование API

- Сценарии тестов: позитивные, негативные, пограничные случаи
    
- Инструменты: Postman, curl, Swagger UI
    
- Анализ требований и спецификаций на полноту
    

---

## 7. 📦 Версионирование API

- `/v1/users`, `/v2/users`
    
- Позволяет не ломать старых клиентов при изменении API
    

---

## 8. 🚫 Ошибки и обработка

- Использование единых структур ошибок:
    

```json
{
  "error": {
    "code": 400,
    "message": "Invalid input"
  }
}
```

- Коды: 4xx — ошибка клиента, 5xx — ошибка сервера
    

---

## 9. 📊 Нагрузочные и нефункциональные требования

- **Ограничение скорости** (Rate Limiting)
    
- **Кэширование** (через заголовки `ETag`, `Cache-Control`)
    
- **Логирование и трассировка** (для анализа проблем)
    

---

## 10. ✅ Лучшие практики

- Чёткие имена эндпоинтов и глаголы — `/users`, `/users/{id}/deactivate`
    
- Использовать глаголы в теле, а не в URL
    
- Стабильные схемы JSON-ответов
    
- Документировать ВСЕ поля, коды ошибок и возможные отклонения
    
- Обсуждать API через диаграммы (например, последовательности)

Ниже пример шаблона Swagger (OpenAPI 3.0) в формате YAML и краткое пояснение:

```yaml
openapi: 3.0.0
info:
  title: User API
  version: 1.0.0
paths:
  /users:
    get:
      summary: Получить список пользователей
      responses:
        '200':
          description: Успешный ответ
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/User'
  /users/{id}:
    get:
      summary: Получить пользователя по ID
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Успешный ответ
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'

components:
  schemas:
    User:
      type: object
      properties:
        id:
          type: integer
        name:
          type: string
        email:
          type: string
```

Этот шаблон описывает API с двумя эндпоинтами: получение списка пользователей и одного пользователя по ID. Его можно визуализировать с помощью Swagger UI или Redoc для быстрой демонстрации и тестирования.
