REST (Representational State Transfer) — архитектурный стиль проектирования распределённых систем, предложенный Роем Филдингом в 2000 году. В контексте API он определяет принципы взаимодействия между клиентом и сервером по протоколу HTTP с акцентом на ресурсы и стандарты.

---

## 📌 Ключевые принципы REST

1. **Идентификация ресурсов** — всё, к чему осуществляется доступ, представлено в виде ресурса с уникальным URL. Пример: `/users/123`, `/orders/456/items`.
    
2. **Унифицированный интерфейс**:
    
    - `GET` — чтение ресурса
        
    - `POST` — создание ресурса
        
    - `PUT` — полное обновление ресурса
        
    - `PATCH` — частичное обновление
        
    - `DELETE` — удаление ресурса
        
3. **Без сохранения состояния (statelessness)** — каждый запрос содержит всю необходимую информацию для его выполнения. Сервер не хранит состояние клиента между запросами.
    
4. **Кешируемость** — ответы могут кешироваться, если это не нарушает корректность взаимодействия.
    
5. **Многоуровневая архитектура** — клиент не должен знать напрямую об архитектуре сервера (может быть промежуточный прокси, балансировщик и т.п.).
    

---

## 🧠 Устройство REST API

### Ресурсы и их представления

- Ресурсы — сущности предметной области (например, пользователь, заказ)
    
- Представления — способы представления ресурсов (JSON, XML, CSV)
    

### Именование и структура URL

- `/users` — список пользователей
    
- `/users/1` — конкретный пользователь
    
- `/users/1/orders` — вложенные ресурсы (связанные сущности)
    

---

## 📐 Форматы данных и взаимодействие

- **Формат запросов и ответов** — чаще всего используется JSON
    
- **Заголовки HTTP**:
    
    - `Content-Type: application/json`
        
    - `Accept: application/json`
        
    - `Authorization: Bearer <token>`
        
- **Коды статуса HTTP**:
    
    - `200 OK` — успешный запрос
        
    - `201 Created` — создан новый ресурс
        
    - `204 No Content` — успешно, без тела ответа
        
    - `400 Bad Request`, `404 Not Found`, `500 Internal Server Error` — ошибки

## 🔧 Примеры [[CRUD]]-операций

### Создание (POST):

```http
POST /users
Content-Type: application/json

{
  "name": "Ivan",
  "email": "ivan@example.com"
}
```

### Чтение (GET):

```http
GET /users/1
```

### Обновление (PUT/PATCH):

```http
PUT /users/1
Content-Type: application/json

{
  "name": "Ivan Petrov"
}
```

### Удаление (DELETE):

```http
DELETE /users/1
```

---

## 🚫 Обработка ошибок

REST предполагает стандартизированный подход:

```json
{
  "error": {
    "code": 400,
    "message": "Invalid input",
    "details": ["email is required"]
  }
}
```

## 🔐 Аутентификация и безопасность

- Basic Auth (не рекомендуется без HTTPS)
    
- OAuth 2.0 (через токены)
    
- [[JWT]] (JSON Web Token)
    
- [[CORS]] (междоменные запросы)
    

---

## 📚 Документация и спецификация

- **OpenAPI (Swagger)** — формальное описание структуры API
    
- **Postman** — коллекции и тестирование запросов
    
- **Swagger UI / Redoc** — визуализация документации
    

---

## ⚙️ Ограничения и нефункциональные аспекты

- Ограничение скорости (Rate Limiting)
    
- Кэширование (ETag, Cache-Control)
    
- Версионирование (`/api/v1/users`)
    
- Логирование и трассировка
    

---

## ✅ Лучшие практики

- Использовать существующие стандарты (HTTP, JSON)
    
- Предсказуемая структура URL и кодов ответа
    
- Использовать ресурсы, а не действия в URL (`/users` вместо `/getUsers`)
    
- Документировать каждый эндпоинт
    
- Стандартизировать обработку ошибок
