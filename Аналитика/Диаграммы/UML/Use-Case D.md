# 🧭 Диаграмма Use Case (вариантов использования): разбор для системного аналитика

## 📌 Введение

**Диаграмма вариантов использования (Use Case Diagram)** — это один из ключевых инструментов в UML, используемый системными аналитиками и архитекторами для визуализации **взаимодействий между пользователями (акторами) и системой**.

Use Case Diagram даёт высокоуровневое представление о функциональности системы и помогает:

- согласовать поведение системы с заказчиком,
    
- определить границы системы,
    
- выявить акторов и роли,
    
- расставить приоритеты в разработке.
    

Холст написан в стиле статей Хабра и будет полезен как аналитикам, так и разработчикам, QA и менеджерам проектов.

---

## 🧠 Что такое диаграмма Use Case

Диаграмма use case — это **визуальное представление всех вариантов использования системы**, при этом каждая диаграмма содержит:

- **акторов** (внешние участники),
    
- **сценарии использования** (use cases),
    
- **связи** между акторами и use case,
    
- **границу системы**, указывающую, что реализуется системой.
    

Диаграмма показывает **что делает пользователь**, а не **как это реализовано**.

---

## 🧍‍♂️ Элементы диаграммы Use Case

### 👤 Актор (Actor)

Участник, взаимодействующий с системой:

- человек (пользователь, менеджер, оператор);
    
- внешняя система (API, CRM, банковская платформа);
    
- роли внутри системы (админ, покупатель).
    

**Обозначение**: человечек / стикман.

### 🧾 Use Case (Сценарий использования)

Функция системы, которую может инициировать актор.

**Обозначение**: овал с названием.

### 🔗 Связь (Association)

Стрелка от актора к сценарию или между сценариями.

Типы связей:

- 🔹 **Include** — включение: один use case всегда вызывает другой
    
- 🔸 **Extend** — расширение: дополнительный функционал, выполняемый по условию
    
- ➡️ **Generalization** — обобщение: иерархия акторов или сценариев
    

### 📦 Система (System Boundary)

Прямоугольник, в который помещаются все use case'ы — это **граница системы**.

---

## 📐 Нотация и обозначения

|Элемент|Символ|Описание|
|---|---|---|
|Актор|👤 Стикман|Внешний участник|
|Use Case|🟠 Овал|Сценарий (например, "Оформить заказ")|
|Include|----> (<>)|Обязательное включение одного сценария в другой|
|Extend|----> (<>)|Расширение сценария при определённых условиях|
|Обобщение|➤|Наследование актора или use case'а|
|Система|📦 Прямоугольник|Ограниченная зона сценариев системы|

## 🧱 Пример: интернет-магазин

### 🎭 Акторы:

- Покупатель
    
- Гость
    
- Администратор
    
- Платёжная система (внешняя)
    

### 🧾 Use Cases:

- Зарегистрироваться
    
- Авторизоваться
    
- Просмотреть каталог
    
- Добавить товар в корзину
    
- Оформить заказ
    
- Оплатить заказ
    
- Отменить заказ
    
- Администрировать товары
    

### 💡 Связи:

- "Оформить заказ" включает "Оплатить заказ"
    
- "Оформить заказ" может быть расширен "Добавить комментарий к заказу"
    
- Актор "Гость" обобщается в "Покупатель"

## 🛠 Где применять диаграммы Use Case

- На этапе **анализа требований**: выявить функции и взаимодействия
    
- При **проектировании архитектуры**: определить границы ответственности
    
- В **технической документации**: как обзорный артефакт
    
- При **разработке UI и UX**: определить точки входа
    
- Для **приоритезации задач** в backlog

## ✅ Преимущества диаграмм Use Case

✔️ Простота восприятия — даже бизнес поймёт, о чём речь  
✔️ Визуальная карта функций системы и её взаимодействий  
✔️ Отличная отправная точка для детализации требований  
✔️ Упрощает обсуждение и документирование границ системы  
✔️ Помогает быстро собрать архитектурный скелет проекта

---

## ⚠️ Ошибки при построении диаграмм

|Ошибка|Почему это проблема|
|---|---|
|🚫 Не связаны акторы с use case|Потеря смысла сценариев|
|🚫 Все use case'ы внутри системы без связей|Нет точек входа, неясны роли|
|🚫 Нет границ системы|Сценарии не структурированы|
|🚫 Нарушение семантики include/extend|Путает реализацию и поведение|
|🚫 Много лишних деталей|Загромождает диаграмму, теряется суть|

---

## 🧩 Советы по построению

- Один use case — одна цель
    
- Показывай только **внешние взаимодействия**, а не внутреннюю логику
    
- Используй **расширения** и **включения** для уменьшения дублирования
    
- Придерживайся единых стандартов и шаблонов в проекте
    
- Не бойся делить диаграмму на несколько — например, для разных ролей

## 📌 Заключение

Диаграмма Use Case — это не просто UML-инструмент, а **мост между бизнесом и технической реализацией**. Системный аналитик, владеющий этим инструментом, может быстро собрать образ системы, зафиксировать роли, выявить пробелы и согласовать цели с командой.

🔍 Ниже — пример диаграммы Use Case в формате PlantUML. Его можно скопировать и визуализировать с помощью PlantUML или интеграции в Draw.io:

```plantuml
@startuml

left to right direction

skinparam packageStyle rectangle

  

actor Guest

actor Customer

actor Admin

actor PaymentSystem as "Платёжная система"

  

rectangle "Интернет-магазин" {

  usecase UC1 as "Зарегистрироваться"

  usecase UC2 as "Авторизоваться"

  usecase UC3 as "Просмотреть каталог"

  usecase UC4 as "Добавить в корзину"

  usecase UC5 as "Оформить заказ"

  usecase UC6 as "Оплатить заказ"

  usecase UC7 as "Отменить заказ"

  usecase UC8 as "Администрировать товары"

  usecase UC9 as "Добавить комментарий"

  

  UC5 --> UC6 : <<include>>

  UC5 --> UC9 : <<extend>>

}

  

Guest --> UC1

Guest --> UC3

Guest --> UC4

Customer --> UC2

Customer --> UC5

Customer --> UC7

Admin --> UC8

PaymentSystem --> UC6

  

Guest -|> Customer

@enduml
```

📌 Можно экспортировать диаграмму в PNG/SVG, встроить в документацию или использовать как основу для детализации use case-сценариев.
