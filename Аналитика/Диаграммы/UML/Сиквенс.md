# ⏱ Диаграмма последовательности (Sequence Diagram) — полный разбор от А до Я

## 📌 Введение

**Диаграмма последовательности** (англ. _Sequence Diagram_) — это один из основных типов диаграмм в языке UML (Unified Modeling Language), применяемый для отображения **порядка обмена сообщениями между участниками системы во времени**. В отличие от других диаграмм UML, фокус диаграммы последовательности направлен на **временную динамику взаимодействий**, а не на структуру или логику отдельно взятых компонентов.

Sequence Diagram позволяет системному аналитику:

- формализовать сценарии взаимодействия в рамках одного use case;
    
- согласовать API-вызовы между модулями, сервисами и компонентами;
    
- зафиксировать нюансы интеграции между frontend и backend;
    
- выявить лишние или отсутствующие шаги в пользовательском или техническом сценарии.
    

---

## 🧱 Базовая структура диаграммы последовательности

Каждая диаграмма последовательности строится на следующих концепциях:

### 👤 Участники (lifelines)

**Линии жизни** представляют собой объекты, компоненты, пользователей, системы, участвующие в сценарии. Они отображаются в верхней части схемы в виде **именованных прямоугольников**, под которыми тянется вертикальная пунктирная линия.

Примеры:

- Пользователь
    
- Мобильное приложение
    
- Backend API
    
- Внешняя система оплаты
    
- База данных
    

### ⏱ Временная ось

Вся диаграмма читается **сверху вниз**, по вертикали — это и есть **ось времени**, по которой выстраиваются события и вызовы. Более высокое положение — более раннее событие.

### ➡️ Сообщения (messages)

Горизонтальные стрелки между линиями жизни:

- **Полные стрелки** — вызовы, команды, события
    
- **Пунктирные стрелки** — ответы, результаты вызова
    

Указывается:

- Название метода / запроса
    
- Параметры
    
- Возвращаемые значения (на стрелке ответа)
    

### ▮ Активация (activation bar)

Вертикальный прямоугольник вдоль линии жизни, указывающий, когда участник активен (выполняет обработку, ждёт ответа и т.д.).

## 🧩 Типовые конструкции в Sequence Diagram

### `alt` — альтернативные потоки

Применяется, когда в сценарии может быть **развилка по условию**:

```plantuml
alt Пользователь найден
  Backend → Frontend: 200 OK + токен
else
  Backend → Frontend: 401 Unauthorized
end
```

### `loop` — цикл

Используется, если одна и та же операция **повторяется**:

```plantuml
loop по каждой записи
  Backend → БД: SELECT ...
end
```

### `opt` — опциональное действие

Описывает **необязательные шаги**, которые выполняются по условию:

```plantuml
opt Запомнить токен
  Frontend → localStorage: save(token)
end
```

### `par` — параллельные действия

Позволяет показать **одновременное выполнение** нескольких потоков:

```plantuml
par отправка SMS
  Система → SMS API
and отправка email
  Система → Email API
end
```

## 📊 Развёрнутый пример: оформление заказа в интернет-магазине

**Участники:**

- `Пользователь`
    
- `Frontend`
    
- `Backend`
    
- `Payment Gateway`
    
- `База данных`
    

```plantuml
Пользователь → Frontend: Нажал "Оформить заказ"
Frontend → Backend: POST /createOrder
Backend → БД: INSERT заказ
БД → Backend: OK (order_id = 10234)
Backend → Payment Gateway: INITIATE PAYMENT (order_id)
Payment Gateway → Backend: CALLBACK + статус оплаты
Backend → БД: UPDATE заказ SET статус = 'оплачен'
Backend → Frontend: 200 OK
Frontend → Пользователь: Заказ оформлен
```

Дополнительно можно вставить `alt` для обработки отказа оплаты и `loop` — если пользователь выбирает товар из нескольких позиций.

## 🎯 Когда использовать Sequence Diagram

|Сценарий|Примеры|
|---|---|
|Проработка бизнес-сценариев|Регистрация, авторизация, покупка, возврат|
|API-интеграции|Вызовы между frontend и backend, взаимодействие с платёжками|
|Асинхронные события|Уведомления, webhooks, pub/sub|
|Моделирование UI-потока|Отправка формы, шаги пользователя|
|Верификация логики межсервисной архитектуры|Сценарии с несколькими backend-сервисами, микросервисами|

## 🧠 Как системный аналитик работает с диаграммами

- 🔍 Анализирует текущее поведение системы (AS IS) — помогает обнаружить скрытые зависимости
    
- 🔧 Проектирует целевое поведение (TO BE) — строит диаграмму будущей логики
    
- 🔄 Валидирует сценарии с разработкой и QA
    
- 🧾 Фиксирует диаграммы в техническом задании или Confluence
    
- 📈 Использует для декомпозиции use case в backend-задачи и контракты API

## 🛠 Инструменты и практики

|Инструмент|Особенности|
|---|---|
|**PlantUML**|Язык разметки → диаграмма, поддержка Git|
|**Draw.io / Diagrams.net**|Ручное построение, drag-and-drop, шаблоны|
|**Lucidchart**|Совместная работа, корпоративный UI|
|**Visual Paradigm**|Продвинутый UML-инструмент|
|**SequenceDiagram.org**|Онлайн, текстовый ввод|

Практика: лучше **проектировать сценарий на черновике**, затем оформлять диаграмму. Используйте **декоративные стили только при необходимости** — содержательность важнее оформления.

## ⚠️ Частые ошибки

|Ошибка|Почему это проблема|
|---|---|
|Не указаны ответы|Нарушает целостность взаимодействия|
|Участники без взаимодействия|Загромождает схему|
|Отсутствует временная логика|Не ясно, кто за кем|
|Смешение логики и UI в одном потоке|Усложняет читабельность|
|Нет условий / альтернативных путей|Потеря бизнес-смысла сценария|
|Слишком большая диаграмма (> 5–6 участников)|Трудно читается, теряется логическая структура|

## 📌 Заключение

Диаграмма последовательности — это **ключевой визуальный инструмент**, который помогает системному аналитику:

- формализовать сценарий до уровня вызовов;
    
- согласовать API и архитектуру;
    
- сделать логику прозрачной и воспроизводимой.
    

Она лежит на стыке анализа, проектирования и тестирования — и именно поэтому так часто входит в **набор артефактов в системном анализе**.
