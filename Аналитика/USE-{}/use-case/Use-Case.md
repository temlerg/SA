# 🧾 Use Case: полный разбор для системного аналитика

## 📌 Введение

**Use Case (вариант использования)** — это один из фундаментальных артефактов системного анализа. Он описывает **взаимодействие между пользователем и системой** для достижения конкретной цели. Несмотря на внешнюю простоту, use case — мощный инструмент, который лежит в основе **технических заданий**, **user story**, **проектной документации**, **тест-кейсов** и **интервью с заказчиком**.

---

## 🧠 Что такое Use Case

Use Case — это **формальное описание сценария взаимодействия пользователя с системой**, которое показывает:

- кто (актор) выполняет действия,
    
- что делает пользователь,
    
- как система на это реагирует,
    
- какая цель достигается.
    

Use Case **не описывает реализацию**, а показывает **поведение системы в терминах взаимодействий**. Это мост между бизнесом и технической реализацией.

---

## 🧍‍♂️ Основные элементы Use Case

|Компонент|Описание|
|---|---|
|**Название**|Краткое, но понятное имя сценария|
|**Актор**|Участник, который инициализирует взаимодействие|
|**Цель**|Что хочет достичь актор через взаимодействие|
|**Предусловия**|Что должно быть выполнено до начала сценария|
|**Основной поток**|Последовательность шагов (система ↔ пользователь)|
|**Альтернативные потоки**|Отклонения от основного, ошибки, исключения|
|**Постусловия**|Что должно быть верным после выполнения|
|**Исключения**|Ошибки и нестандартные ситуации|
|**Бизнес-правила**|Правила и ограничения, связанные со сценарием|

## 📋 Пример use case (регистрация пользователя)

**Название:** Регистрация нового пользователя  
**Актор:** Нерегистрированный пользователь  
**Цель:** Создание учётной записи для входа в систему  
**Предусловия:** Пользователь не авторизован и не зарегистрирован

### Основной поток:

1. Пользователь нажимает на кнопку "Зарегистрироваться"
    
2. Система отображает форму регистрации
    
3. Пользователь вводит email, пароль, подтверждение пароля
    
4. Система проверяет валидность email и пароля
    
5. Система сохраняет данные пользователя
    
6. Система отправляет email с подтверждением
    
7. Пользователь получает сообщение об успешной регистрации
    

### Альтернативные потоки:

- 3а. Пользователь вводит некорректный email → Система показывает сообщение об ошибке
    
- 4а. Пароль не соответствует требованиям → Система не позволяет продолжить
    

### Постусловия:

- Пользователь создан в базе данных
    
- Установлен статус "требуется подтверждение email"
    

---

## 🎯 Зачем нужен Use Case

- 🛠 **Для аналитика:** фиксирует поведение системы и границы ответственности
    
- 🧑‍💼 **Для заказчика:** помогает визуализировать сценарии взаимодействия
    
- 💻 **Для разработчика:** служит технической спецификацией
    
- 🧪 **Для тестировщика:** основа для написания тест-кейсов
    
- 📜 **Для документации:** включает в ТЗ, wiki, Confluence, Jira
    

---

## 🔍 Use Case vs. User Story vs. Диаграмма Use Case

|Критерий|Use Case|User Story|Диаграмма Use Case|
|---|---|---|---|
|Формат|Текстовая спецификация|Однострочная формулировка|UML-диаграмма с актёрами|
|Глубина|Подробная|Поверхностная, абстрактная|Визуализация связей|
|Применение|ТЗ, анализ, тестирование|Agile-планирование|Архитектура, обзор|
|Пример|5–10 шагов с условиями и ошибками|"Как пользователь, я хочу..."|Актор → Система (линии)|

## 🧠 Как писать Use Case — пошагово

### 1. 📚 Сбор сценариев

- Интервью с заказчиком
    
- Анализ CJM / BPMN / бизнес-процессов
    
- Анализ багов, инцидентов, пожеланий клиентов
    

### 2. ✍️ Формулировка основной цели

- Что пользователь хочет сделать?
    
- Почему это важно?
    
- В каком контексте запускается сценарий?
    

### 3. 👤 Выделение актёров

- Кто взаимодействует с системой?
    
- Есть ли вторичные актёры (например, служба поддержки)?
    

### 4. 🪜 Построение основного потока

- Последовательно, в логике «Пользователь → Система → Пользователь»
    
- Указывать только значимые шаги, а не UI-детали
    

### 5. 🔀 Добавление альтернатив и исключений

- Что может пойти не так?
    
- Как система должна реагировать на ошибку?
    

### 6. 📃 Уточнение бизнес-правил и ограничений

- Например: только один активный заказ, проверка возраста, GDPR
    

### 7. ✅ Валидация с заказчиком и командой

- Use case должен быть понятен и бизнесу, и разработчику

## 🧾 Расширенные конструкции

### 🔁 Вложенные use case (inclusion)

Иногда один use case вызывает другой:

- UC001: Оформление заказа
    
- UC002: Выбор способа оплаты → включается в UC001
    

### ↩️ Расширения (extensions)

Use case может **расширяться** дополнительными шагами, если выполняется определённое условие:

- UC003: Добавить подарок к заказу (если сумма > 5000)
    

### 🔒 Preconditions/Postconditions

- `Предусловие:` Пользователь авторизован
    
- `Постусловие:` Создан заказ со статусом "в ожидании оплаты"
    

---

## 💡 Практические советы

- Пиши **в третьем лице**, от имени наблюдателя: "Пользователь нажимает кнопку"
    
- Не пиши UI-детали: "Кнопка зелёная" — неважно
    
- Один use case = одна цель. Не описывай сразу оплату, возврат, доставку
    
- Разделяй бизнес-логику и тех. реализацию
    
- Упрощай: чем понятнее use case, тем лучше он работает

## ⚠️ Типичные ошибки системных аналитиков

|Ошибка|Почему это плохо|
|---|---|
|🚫 Use case без цели|Нет смысла в сценарии|
|🚫 Смешение нескольких сценариев|Путает разработку и тестирование|
|🚫 Упоминание UI-элементов|Привязка к реализации|
|🚫 Нет альтернативных и исключающих путей|Нет полноты|
|🚫 Нет условий начала и окончания|Неясно, где начинается и где заканчивается|

## 📌 Заключение

Use Case — это **универсальный инструмент системного анализа**, позволяющий задокументировать поведение системы на уровне взаимодействий. Он является мостом между бизнесом и реализацией, помогает выявлять неполноту, строить тест-кейсы и писать надёжное техническое задание.
