# 🎤 Вопросы и ответы на собеседовании системного аналитика (Middle)

## 🧠 Общие вопросы

**1. Чем занимается системный аналитик?**  
Формализует требования, проектирует архитектуру решений, описывает поведение системы.

**2. Разница между бизнес- и системным аналитиком?**  
Бизнес-аналитик выявляет цели, системный — описывает реализацию.

**3. Что такое функциональные и нефункциональные требования?**  
Функциональные — «что делает система». Нефункциональные — «как она работает» (производительность, отказоустойчивость).

**4. Что такое Use Case?**  
Пошаговое описание сценария взаимодействия с системой.

**5. Чем отличается Use Case от User Story?**  
Use Case — подробный алгоритм. Story — краткое описание цели пользователя.

---

## 🌐 API и интеграции

**6. Что такое REST?**  
Архитектурный стиль API. Методы: GET, POST, PUT, DELETE. Форматы: JSON.

**7. Чем отличается REST от SOAP?**  
SOAP — формальный, с XML и WSDL. REST проще, на HTTP, с JSON.

**8. Что такое Swagger?**  
Инструмент для описания и тестирования REST API (OpenAPI).

**9. Что такое синхронная и асинхронная интеграция?**  
Синхронная — ответ сразу (REST). Асинхронная — позже (Kafka, очередь).

**10. Что такое webhook?**  
Асинхронный вызов системы на внешний URL при событии.

---

## 💾 Базы данных

**11. Разница между SQL и NoSQL?**  
SQL — таблицы и строгая схема. NoSQL — документы, графы, ключ-значение.

**12. Что такое нормализация?**  
Процесс разбиения таблиц для устранения дублирования данных.

**13. Что такое индекс?**  
Структура, ускоряющая поиск по полям.

**14. Какие типы индексов знаете?**  
B-Tree, Hash, Full-text, GIN, BRIN.

**15. Что такое транзакция?**  
Набор операций, которые выполняются как единое целое (ACID).

---

## 📊 Диаграммы и моделирование

**16. Что такое диаграмма классов?**  
UML-схема сущностей, их атрибутов и связей.

**17. Чем отличается Activity от BPMN?**  
Activity — UML-процессы. BPMN — бизнес-процессы с ролями, событиями и потоками.

**18. Что такое диаграмма состояний?**  
Показывает переходы объекта между состояниями.

**19. Что такое ER-диаграмма?**  
Модель сущностей, их атрибутов и связей (Entity-Relationship).

**20. Что такое use case диаграмма?**  
Схема, показывающая акторов и их сценарии взаимодействия с системой.

---

## 📋 Работа аналитика

**21. Какие артефакты создаёте?**  
Use Case, диаграммы, user stories, API-документация, ТЗ, таблицы, глоссарии.

**22. Какие инструменты используете?**  
Draw.io, Postman, Swagger, Confluence, Jira, DBeaver, pgAdmin.

**23. Как определяете приоритет требований?**  
Методы MoSCoW, бизнес-ценность, риски и затраты.

**24. Как работаете с требованиями?**  
Собираю → формализую → согласую → трассирую → обновляю.

**25. Что такое MVP?**  
Минимально жизнеспособный продукт, содержащий ключевой функционал.

## 🛠 Технические нюансы

**26. Что такое idempotency?**  
Свойство API-запроса не менять результат при повторном вызове.

**27. Что такое SLA?**  
Соглашение об уровне сервиса: доступность, время ответа, поддержка.

**28. Как описываете API?**  
Схема endpoints, методы, параметры, ответы, коды ошибок, модели данных.

**29. Что такое схема данных?**  
Описание структуры: таблицы, поля, типы, связи (ER-диаграмма).

**30. Как отследить соответствие требований и реализации?**  
С помощью трассировочной матрицы (traceability matrix).

## 🎯 Кейс-вопросы и практические ситуации

**Кейс 1. Интернет-магазин.**  
_Задача:_ Клиент жалуется, что после оформления заказа не получил уведомления.  
**Вопрос:** Как вы будете анализировать проблему?  
**Ответ:** Проверю бизнес-процесс оформления (BPMN), сценарий отправки уведомлений (Use Case), логи и настройки интеграции с почтовым сервисом.

**Кейс 2. Банк.**  
_Задача:_ Нужно реализовать функцию досрочного закрытия вклада.  
**Вопрос:** Как сформируете требования?  
**Ответ:** Проведу интервью с бизнесом, уточню ограничения, опишу сценарии (use case), нарисую диаграмму состояний вклада, подготовлю API-контракт.

**Кейс 3. Логистика.**  
_Задача:_ Курьер не может принять заказ в приложении.  
**Вопрос:** Что проверите?  
**Ответ:** Диаграмму состояний заказа, UI-флоу курьера, связку с REST API, валидность JWT.

**Кейс 4. CRM-система.**  
_Задача:_ Заказчики просят интеграцию с новым внешним API.  
**Вопрос:** С чего начнёте?  
**Ответ:** Соберу контракт API, опишу формат данных, выберу способ интеграции (синхронная/асинхронная), опишу точки входа и логику обработки.

**Кейс 5. Финтех.**  
_Задача:_ Нужна валидация email при регистрации.  
**Вопрос:** Как опишете?  
**Ответ:** Добавлю ограничение в нефункциональные требования, опишу RegExp в спецификации, добавлю критерий приёмки в story. 

## ❓ Каверзные и проверочные вопросы

**1. Чем отличается extend от include в use case?**  
Include — обязательная вставка (переиспользуемый шаг), extend — условное расширение, которое может не происходить.

**2. REST API возвращает 204 — что это значит?**  
Успешный ответ без тела. Например, после успешного DELETE.

**3. Можно ли вставить NULL в PRIMARY KEY?**  
Нет. PRIMARY KEY требует уникальности и NOT NULL.

**4. В чём разница между LEFT JOIN и INNER JOIN?**  
LEFT JOIN возвращает все строки из левой таблицы. INNER — только совпавшие.

**5. Какие статусы HTTP использует редирект?**  
301 (постоянный), 302 (временный), 307 (сохранение метода).

**6. Когда использовать BPMN вместо activity diagram?**  
Когда нужен фокус на ролях, интеграциях и бизнес-событиях.

**7. Что такое race condition?**  
Конфликт при параллельном доступе к ресурсу без синхронизации.

**8. Чем отличаются optimistic и pessimistic lock?**  
Optimistic — проверка на конфликт при записи. Pessimistic — блокировка сразу при чтении.

**9. Можно ли вложить use case в другой?**  
Да — через include или extend в UML.

**10. Каковы риски в API без версионирования?**  
Ломаются клиенты при любом изменении контракта. Невозможно поддерживать обратную совместимость.

## 🧪 Мини-кейс: SQL и диаграмма

**SQL:**  
Таблица `orders`: id, user_id, amount, status, created_at.  
**Вопрос:** Напишите запрос для получения суммы заказов за март 2024 со статусом 'paid'.

```sql
SELECT SUM(amount) 
FROM orders 
WHERE status = 'paid' AND created_at BETWEEN '2024-03-01' AND '2024-03-31';
```

**Диаграмма:**  
Use Case «Оформить заказ» включает «Выбрать адрес» и может расширяться «Оплатить через бонусы».  
**Вопрос:** Что из них include, что extend?  
**Ответ:** «Выбрать адрес» — include (обязательная часть), «Оплатить через бонусы» — extend (опционально).

## 🔍 Практика по REST API и бизнес-процессам

**API-сценарий 1.**  
Клиент вызывает `GET /user/123`, получает 403.  
**Вопрос:** Что может быть причиной?  
**Ответ:** Нет авторизации, JWT истёк, ACL запрещает доступ к ресурсу.

**API-сценарий 2.**  
При `POST /orders` клиент получает 500.  
**Вопрос:** Как будете анализировать?  
**Ответ:** Проверю: тело запроса, схему модели, валидацию на сервере, логи, исключения в сервисе оформления.

**API-сценарий 3.**  
Старый клиент отправляет POST без поля `email`, а сервер его требует.  
**Вопрос:** Как сохранить совместимость?  
**Ответ:** Ввести версионирование: `POST /v1/orders`, `POST /v2/orders`.

**Бизнес-процесс: регистрация пользователя через email**  
**Этапы:**\

1. Пользователь вводит email\
    
2. Система проверяет, не зарегистрирован ли он\
    
3. Генерирует ссылку и отправляет письмо\
    
4. Пользователь переходит по ссылке\
    
5. Система активирует учётную запись
    

**Вопрос:** Где возможны сбои?\

- Отказ почтового сервиса\
    
- Таймаут ссылки\
    
- Повторный переход по ссылке
    

**Как покрыть:**\

- Диаграмма activity или BPMN с исключениями\
    
- Use case с альтернативными потоками\
    
- Обработка повторной регистрации
    

## 📬 Вопросы по message brokers (Kafka, RabbitMQ) и edge-cases CRUD

**1. Что такое message broker?**  
Компонент, обеспечивающий асинхронный обмен сообщениями между системами (pub/sub, очередь).

**2. Kafka vs RabbitMQ — в чём разница?**  
Kafka — log-based, быстрый, хорошо для стриминга. RabbitMQ — message-based, надёжен, гибко настраиваемый.

**3. Что такое topic и partition в Kafka?**  
Topic — канал сообщений. Partition — горизонтальное разбиение топика для параллелизма.

**4. Что такое ACK и DLQ?**  
ACK — подтверждение получения. DLQ (dead letter queue) — очередь для неуспешных сообщений.

**5. Где аналитик применяет Kafka?**  
Анализ схем взаимодействия, описание топиков, продюсеров и консьюмеров, трассировка событий.

---

**CRUD edge-case 1.**  
_Удаление клиента_ — что если у него есть заказы?  
**Ответ:** Нужна проверка внешних связей. Варианты: запрет, каскад, логическая пометка (is_deleted).

**CRUD edge-case 2.**  
_Обновление заказа_ после доставки.  
**Ответ:** Добавить контроль статуса: запрещать UPDATE при status = 'delivered'.

**CRUD edge-case 3.**  
_Создание дубликатов при повторной отправке формы._  
**Ответ:** Использовать idempotency token или уникальный индекс.

**CRUD edge-case 4.**  
_Чтение неактуальных данных при высокой нагрузке._  
**Ответ:** Уточнить требования к консистентности. Возможно, применить кеширование или версионирование.

**CRUD edge-case 5.**  
_Удаление записи, к которой есть активные подписки._  
**Ответ:** Предусмотреть soft delete, или добавить механизм обратной синхронизации и уведомлений.

## 🧱 Архитектурные решения и тестирование интеграций

**1. Что такое событийная модель (Event-driven architecture)?**  
Система, где модули обмениваются событиями (publish/subscribe), а не синхронными вызовами. Повышает масштабируемость и слабую связанность компонентов.

**2. Что такое CQRS?**  
Command Query Responsibility Segregation — разделение операций записи (command) и чтения (query). Чтение — оптимизировано под отчёты, запись — под бизнес-логику.

**3. Что такое API Gateway?**  
Шлюз, через который идут все запросы к микросервисам. Реализует маршрутизацию, авторизацию, агрегацию, троттлинг и кеширование.

**4. Как тестировать интеграции?**

- Использовать **моки** и **стабы** для изолированной проверки
    
- Поднимать **test-containers** (PostgreSQL, Kafka) во время CI
    
- Автоматизировать сценарии с Postman/Newman или REST-assured
    
- Проверять граничные случаи: таймауты, ошибки API, нестабильные ответы
    

**5. Что такое contract testing?**  
Тесты, проверяющие соответствие между API-клиентом и сервером. Позволяют выявить изменения в интерфейсе. Инструменты: Pact, Spring Cloud Contract.

**6. Какие проблемы решает событийная модель?**

- Расширяемость (можно подключать новых подписчиков)
    
- Декуплинг модулей
    
- Возможность ретроспективной аналитики
    

**7. Когда использовать CQRS?**

- При высокой нагрузке на чтение
    
- При сложной валидации записи
    
- Когда нужны разные модели для UI и логики
    

**8. В чём риск API Gateway?**

- Становится точкой отказа
    
- Требует защиты (auth, rate-limit)
    
- Повышает задержку, если неправильно настроен
    

## ⚙️ Вопросы по DDD, микросервисам и CI/CD

**1. Что такое DDD?**  
Domain-Driven Design — подход, при котором бизнес-логика и модель системы строятся вокруг предметной области. В центре — Ubiquitous Language.

**2. Что такое bounded context?**  
Ограниченный контекст, внутри которого терминология и бизнес-правила едины. Используется для разделения доменов в DDD.

**3. В чём плюсы микросервисной архитектуры?**  
Изоляция, независимая разработка и деплой, масштабируемость, устойчивость к сбоям.

**4. В чём минусы микросервисов?**  
Сложности с интеграцией, мониторингом, согласованностью данных, DevOps-нагрузка.

**5. Что такое CI/CD?**  
Continuous Integration / Continuous Delivery — процессы автоматической сборки, тестирования и доставки кода в продакшн.

**6. Какие инструменты CI/CD знаете?**  
Jenkins, GitLab CI, GitHub Actions, TeamCity, CircleCI, ArgoCD.

**7. Как аналитик участвует в CI/CD?**  
Подготавливает test-кейсы, критерии приёмки, спецификации для автоматизированных тестов.

**8. Что такое feature toggle?**  
Механизм, позволяющий включать/выключать функциональность без деплоя, часто используется в CD.

**9. Чем отличается Canary release от Blue-Green deployment?**  
Canary — поэтапный выпуск на часть пользователей. Blue-Green — переключение между двумя идентичными окружениями.

**10. Что такое конфигурация как код (Configuration as Code)?**  
Подход, при котором инфраструктура и параметры окружения описываются в виде версионируемого кода (Terraform, Helm, Ansible).
